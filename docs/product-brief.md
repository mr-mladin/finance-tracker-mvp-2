# Product brief: Finance Tracker MVP 2

## Главная идея

Сделать не витрину, а рабочий личный финансовый инструмент: доходы, расходы, переводы между счетами, планы, отчеты, бюджеты, цели и синхронизация между устройствами.

Референсы по UX:

- Money Flow: привычный, плавный, удобный мобильный интерфейс.
- Дзен-мани: сильные блоки доходов/расходов/остатка, планирования, аналитики и сравнения расходов.
- Apple Liquid Glass: использовать только как аккуратный акцент, не заливать им весь интерфейс.

Главный принцип: чисто, премиально, спокойно, удобно читать цифры. Финансы любят порядок.

## Главный дашборд

На главной странице обязательно должен быть блок "Доходы и расходы".

Логика блока:

- Доходы: зеленый тонкий индикатор заполняется слева направо.
- Расходы: темный тонкий индикатор заполняется слева направо пропорционально расходам от дохода.
- Остаток: бирюзовый тонкий индикатор расположен справа и уменьшается справа/с противоположной стороны по мере роста расходов.
- Чем больше расходов, тем меньше остаток.
- Все три строки должны быть функциональными, считаться из операций, а не быть статичной картинкой.
- Индикаторы должны быть тонкими, с мягкими скруглениями, визуально близкими к референсу из Дзен-мани.
- Важный показатель: "Доля расходов" можно показывать простыми словами: "Потрачено от дохода в этом месяце".

На главной также нужен блок "Планы":

- график фактических доходов и расходов;
- продолжение плановых доходов и расходов пунктиром;
- фактический доход зеленой линией;
- фактический расход темной линией;
- плановый доход продолжает зеленую линию пунктиром;
- плановый расход продолжает линию расходов пунктиром;
- если плановые расходы приводят к отрицательному балансу, проблемный участок подсвечивается красным;
- при наведении на день показываются доходы, расходы, баланс и операции этого дня.

## Основные сущности

MVP должен закладывать нормальную структуру:

- счета;
- операции;
- доходы;
- расходы;
- переводы между своими счетами;
- категории доходов;
- категории расходов;
- подкатегории;
- теги;
- комментарии;
- дата операции;
- сумма операции;
- валюта, по умолчанию рубль.

Переводы между своими счетами не считаются доходом или расходом.

## Счета

Нужны пользовательские счета:

- наличные;
- карты;
- накопления;
- любые свои счета.

Пользователь должен уметь:

- создавать счета;
- редактировать счета;
- удалять счета;
- менять порядок счетов перетаскиванием мышкой;
- выбирать цвет счета;
- выбирать иконку счета;
- использовать emoji как иконку счета.

Суммы всегда отображать с пробелами: "100 000", не "100000".

## Категории, подкатегории, теги

Пользователь должен уметь:

- создавать категории доходов;
- создавать категории расходов;
- создавать подкатегории;
- создавать теги;
- редактировать их;
- удалять их;
- менять порядок перетаскиванием мышкой;
- выбирать цвет;
- выбирать иконку или emoji.

Нужна многоуровневая структура категорий:

- пример: Образование -> Андрей -> Наставничество;
- пример: Образование -> Юлия -> Курс.

Категории в форме операции не должны дублироваться.

## Операции

Добавление операции должно быть быстрым:

- тип: доход / расход / перевод;
- счет;
- счет списания и счет зачисления для перевода;
- категория;
- подкатегория;
- теги;
- комментарий;
- дата;
- сумма;
- статус: факт / план.

Пользователь должен уметь:

- создавать операции;
- редактировать операции;
- дублировать операции;
- удалять операции;
- быстро повторять похожую операцию.

В списке операций:

- показывать дату;
- показывать категорию;
- показывать счет;
- показывать комментарий/название;
- показывать сумму с плюсом или минусом;
- доходы зеленые;
- расходы темные или красные по смыслу;
- лишние стрелки лучше убрать, если плюс/минус и цвет уже дают контекст;
- группировать операции по дням;
- показывать сумму дня.

## Отчеты и аналитика

Нужна отдельная вкладка отчетов:

- бублик расходов по категориям;
- динамика доходов и расходов по дням, неделям, месяцам;
- сравнение расходов за два периода;
- тренды расходов и доходов.

Сравнение расходов:

- выбрать два периода;
- сравнить общие расходы;
- показать разницу в рублях и процентах;
- показать категории, которые выросли;
- показать категории, которые снизились.

Тренды:

- расходы на категорию выросли/упали за период;
- доход по источнику вырос/упал за период;
- примеры: "Продукты выросли на 37% за 3 месяца", "Интернет снизился на 50%".

## Планы

Планы должны быть одним из ключевых разделов.

Нужны:

- запланированные доходы;
- запланированные расходы;
- просмотр планов по дням;
- баланс на выбранный день;
- прогноз свободных денег до конца месяца;
- предупреждение, если денег может не хватить;
- список плановых операций;
- возможность добавить плановый платеж.

## Бюджеты и цели

Бюджеты:

- бюджет по категории;
- факт против плана;
- предупреждение о превышении.

Цели:

- цель накопления;
- целевая сумма;
- счет, на котором копятся деньги;
- не поле "уже накоплено", а привязка к счету.

## Настройки

Нужен полноценный раздел настроек:

- тема: светлая / темная / автоматическая;
- основная валюта;
- формат сумм;
- первый день недели;
- начало финансового месяца, если понадобится;
- управление счетами;
- управление категориями;
- управление подкатегориями;
- управление тегами;
- экспорт данных;
- импорт данных.

## Данные и синхронизация

Данные не должны теряться при смене компьютера.

Нужно:

- авторизация;
- отдельный Supabase-проект для нового MVP;
- хранение данных в облаке;
- экспорт данных;
- импорт данных из банковских выгрузок;
- возможность восстановить доступ с другого компьютера или телефона.

Старый Supabase-проект и старые ключи не использовать.

## Дизайн

Направление:

- чистый светлый интерфейс;
- больше воздуха;
- меньше фиолетового;
- основной акцент: мягкий зеленый;
- Liquid Glass только как акцент;
- не использовать устаревшие градиенты "фиолетовый-зеленый";
- цифры должны читаться быстро;
- интерфейс должен выглядеть так, будто над ним работал живой профессиональный дизайнер.

Мобильная адаптация обязательна.

## Не делать

- Не превращать MVP в комбайн имени Минсельхоза.
- Не делать красивые, но нефункциональные картинки.
- Не дублировать кнопки, если действие можно выполнить за один клик.
- Не заставлять пользователя дважды нажимать "Создать счет".
- Не хранить новый проект вперемешку со старым.
- Не использовать старые Supabase-ключи.
- Не делать громоздкий glassmorphism ради glassmorphism.
